# 1.7 plan: touch control through the eye, and forced landscape

Status: approved (touch control option A + forced landscape policy field) and implemented in 1.7.0-EN.

## Goal

Control the app on a virtual display by touching its picture in the eye viewer: taps, swipes, scrolling, pinch
(multi-touch), plus a Back button. The display itself is still never recreated or resized.

## Touch in the full-screen viewer (option A)

**A picture-in-picture window can't receive touches**: Android keeps taps on a PiP window for its own controls
(tap shows the PiP buttons, drag moves it), and no app can change that. So touch works in the **full-screen
viewer**: tap PiP → expand → use the app by touch → shrink back to PiP. PiP itself stays view-only.

## How touch works

```
viewer (full screen or floating window)
   │ touch on the picture → position mapped to the display's own pixels
   ▼ (letterbox bars ignored; multi-touch, all pointers)
compact touch events over a pipe (opened once, kept open while the viewer is up)
   ▼
daemon (system_server with Vector, or the Shizuku service) → InputManager.injectInputEvent(event, displayId)
   ▼
app on the virtual display receives normal touches
```

- **Fast:** one pipe for the whole session instead of one call per touch, so touches arrive within a frame or two.
- **Two different Backs:**
  - the **Back button in the viewer's controls** goes to the app on the virtual display;
  - the **tablet's own Back** (gesture or navigation bar) and **Home** are always yours: Back shrinks the viewer to
    PiP, Home leaves it, giving you the built-in screen back.
- **Both channels:** Vector (system_server) and Shizuku (shell) can both inject input.
- **Works while casting:** touch the eye while the TV shows the picture.

## Safety

- Only MoreDisplay itself may open the touch pipe (same check as the eye's surface and cast sound).
- Touches are only ever injected into **managed virtual displays**, never into the built-in screen or another
  app's display.
- The pipe closes when the viewer closes or dies, and injection stops at once.

## Forced landscape for an app (new policy field)

**What happens now:** the virtual display is 1280×720 (landscape) and is never rotated (your tablet's rotation lock
doesn't affect it). But many phone apps ask Android for **portrait**. A virtual display can't turn, so Android 12L
keeps the app upright and shows it as a narrow portrait strip in the middle of the landscape display, with black
bars on the sides ("letterboxing"). Android has no launch flag that changes another app's orientation.

**Fix:** a new **Orientation** field in the app's policy:

| Orientation | Effect |
| --- | --- |
| As the app wants (default) | Unchanged. |
| Landscape | Every time the app asks for portrait (when it starts, or later from code), MoreDisplay answers landscape instead. The app gets a landscape screen and fills the 1280×720 display. |

- How: in system_server, the single place where Android records an activity's requested orientation
  (`WindowContainer#setOrientation(int, WindowContainer)`, present on Android 12L and later) is hooked: for the
  app's activities a portrait request becomes landscape, and the activity's declared orientation is changed the same
  way so Android doesn't apply its compatibility letterbox either. Checked against the Android 12L source.
- It applies to the app wherever it is shown, so it's meant for apps set to **Open on** a virtual display.
- Saved and restored after reboots like the other policy fields; adb: `--es orientation landscape`.
- Limit: an app built only for portrait may look stretched or oddly laid out in landscape. Video apps are
  usually fine.

## Settings

| Setting | Default |
| --- | --- |
| Touch control in the eye | on |
| Show touches (a small dot where you touch, in the viewer only) | off |

## Keeping the tablet's Back and Home yours

Checked in the Android 12L source: a touch on another display moves Android's input focus to that display
(`WindowManagerService#onPointerDownOutsideFocusLocked`). After that, the built-in screen has no focused window, so
the tablet's Back would be lost, and a physical Back key or keyboard would go to the hidden app.

So when each touch gesture ends (finger up), the daemon gives focus back to the viewer
(`ActivityTaskManager#setFocusedTask(viewer task)`, which moves the built-in screen back on top). The hidden app
keeps running and drawing normally; it only stops being the keyboard target, which this version doesn't use.

## Code changes

| Area | Change |
| --- | --- |
| RPC | `OpenTouchChannel(displayId)` with the pipe's read end + token next to it (like cast sound); protocol 22 |
| Policy | `DisplayPolicy.orientation` (codec, persistence, editor, policy list, adb) |
| Hooks | `OrientationHooks`: portrait requests → landscape for apps with the field set |
| Daemon | `TouchInjector`: reads events, rebuilds `MotionEvent`s with the display id, injects them; Back key; gives focus back to the viewer's task after each gesture |
| Eye | touch mapping in `ViewerActivity` (content rectangle only), Back button, optional touch dots |
| Settings | the two switches above |
| Tests | event encoding/decoding, coordinate mapping, orientation mapping, policy persistence (pure Kotlin) |
| Docs | README "Touch control" and "Orientation", CHANGELOG; version 1.7.0-EN |

## Not included (possible later)

- Typing with the tablet's keyboard into the hidden app.
- Mouse/keyboard from a connected hardware keyboard.
- A floating touch window over other apps (option B), as a possible later step.
